# Master PRD implementation traceability

This matrix maps the Master PRD v1.0 to the current implementation and its evidence. “Verified with test data” means a workflow passed against a disposable database; it does not certify the configured company's opening balances, legal/tax treatment, or production deployment. See [`UAT.md`](UAT.md) for dated run details and [`IMPLEMENTATION_STATUS.md`](IMPLEMENTATION_STATUS.md) for implementation history.

| PRD requirement | Current implementation and strongest evidence | Remaining acceptance / dependency |
| --- | --- | --- |
| Setup, sign-in, roles and permissions (PRD §§2, 6, 25) | First-run Owner setup, closed public signup, shared sign-in, Owner-created staff, predefined roles, session management, optional TOTP and scoped API permissions. Fresh-database integration covers Owner, Manager, Cashier, Accountant and operational roles; live Owner screens load. | Owner review of configured roles and the active “QA branch user” Auditor account. Confirm Manager approval limits before relying on them. |

| Business masters and units (PRD §8.2) | Customer, supplier, broker, employee, vehicle, driver, product, chamber, category, tax-code and unit workflows are implemented; conversion snapshots preserve base quantities. Customer/driver portals, GPS, WhatsApp ordering, IoT, predictive AI and complex multi-currency are explicitly future/non-goals for v1. | Implement only after the Owner approves scope and any provider/business requirements. |

## Business decisions still requiring an authorized reviewer

- Tax, GST, e-invoice/e-way bill applicability and statutory filing/report behavior require CA review.
- Payroll statutory and overtime rules, opening balances, historic inventory valuation, broker terms, rates and approval limits require Owner/accountant input.
- Stock/COGS cutoff is resolved: the Owner selected invoice posting.
- Physical-device UAT, populated-company reconciliation and production launch sign-off remain outstanding.
